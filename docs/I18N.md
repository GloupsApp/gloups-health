# International users

Worldwide launch with French and English first is confirmed. This guide records
requirements for future implementation; no catalogs or locale resolver exist yet.

## Independent settings

| Concept           | Requirement                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| Language          | Complete English/French UI, native labels, accessibility, errors, coach messages and required public copy  |
| Formatting locale | Region-aware dates, numbers, plural forms and time formats; a French speaker need not use France's formats |
| Timezone          | Explicit IANA zone for local-day and recurring behavior, independent of language or country                |
| Units             | Explicit measurement preferences and canonical stored units, independent of formatting and language        |
| Country/market    | Eligibility, distribution, catalog coverage and provider/legal availability; not inferred from language    |
| Currency          | Actual store/provider offer currency and formatting; never a guessed conversion from interface language    |

Resolve supported language from explicit preference, then preferred device
languages, then English. Preserve a user override. Keep complete en/fr catalogs
with parity checks once tooling exists. Use message keys, plural-aware messages
and named interpolation, without concatenating translated sentence fragments.
API/domain values and error codes remain language neutral. Store original coach
language/context; changing UI language must not rewrite historical records.

Use Unicode text and names. Support diacritics, variable text length, font
scaling and accessibility on both platforms. Additional scripts and right-to-left
languages are future locales, but do not hard-code left/right or ASCII-only
identities into shared contracts.

## Dates and durable records

Define instants, intervals and local calendar dates separately. Store an IANA
zone where civil time matters; an offset alone cannot define future recurrence.
Do not represent a date-only record as implicit UTC midnight. Define the local
day used for meals, sleep, cycle, coaching and quotas in each contract.

Handle DST gaps/overlaps, travel across zones/date lines, overnight sleep, naps,
shift work and historical edits. Changing a display zone cannot silently move a
saved meal or cycle date. Recurring reminders need an explicit zone policy and
must not double-send or disappear because a day has 23 or 25 hours.

Do not parse ambiguous strings such as 03/04/2026 as wire dates. Accept localized
input explicitly, return validation errors in the chosen language and transport
unambiguous values. UI formatting cannot determine record identity or sort order.

## Numbers, units, food and billing

Define canonical stored units and preserve accepted input/provenance. Convert at
boundaries using documented factors and rounding. Distinguish energy, mass,
height, distance, water volume and exercise load; do not treat US/Imperial fluid
ounces as the same unit or silently reinterpret a stored load after a preference
change. Support decimal comma/dot and regional grouping in input without lossy
string replacements.

Catalog source/region, barcode, branded name and serving definition are separate
from interface language. Verify coverage and licenses before promising a global
food database. Show unavailable coverage instead of inventing nutrient values.

Use the real localized store offer/currency/tax presentation. Recurring billing,
country eligibility and legal text need market review. Worldwide is not evidence
that every store territory, health adapter or provider already supports Gloups.

## Required acceptance

Check both languages with multiple formatting regions, metric and supported
nonmetric units, 12/24-hour clocks and different week starts. Include DST in both
hemispheres, half/quarter-hour zones, date-line travel, decimal-comma input,
midnight retries, overnight sleep and denied permissions. Exercise actual app/API
boundaries and catalog parity checks; do not add unit tests for these rules.

Keep a release matrix of supported locales, stores/markets, providers, actual
devices and known restrictions before worldwide availability is announced.
