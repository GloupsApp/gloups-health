# Backend organization and dependency rules

Organize code by business capability under `src/modules`, using familiar Nest component names inside each feature. Keep small features flat; add `commands`, `queries`, `controllers`, `guards`, `services`, `integrations`, or `workers` folders when navigation benefits. Do not repeat architectural-layer folders or create modules solely to register a layer. Create a submodule when it owns a capability or isolates a runtime. Keep HTTP and worker entry points separate when both exist.

Use extensionless feature aliases for application and application-test imports, such as `@accounts/commands/resolve-account.service`, `@authentication/public`, and `@database/public`. Keep the root test aliases and application compiler aliases aligned. TypeScript checks these source paths; `tsc-alias` rewrites emitted JavaScript and declaration imports for Node ESM. Do not add `.js` suffixes or parent-directory chains to authored application imports. Generated vendor sources retain their generator's conventions. Aliases still obey the same public feature contracts and dependency checks.

Business models, repository/session ports, and business operations designated as plain stay independent of Nest, transport contracts, Drizzle, and provider SDKs. Nest can construct a plain service with a factory provider in its owning feature module. Controllers, guards, and pipes handle transport/admission; services coordinate operations; models own invariants; repositories and integrations own external details. Better Auth owns authentication mechanics; Gloups owns account identity, ownership, and lifecycle rules.

Use Nest CQRS for Gloups-owned commands and queries. Register `CqrsModule.forRoot()` once in the application entry point. Messages remain plain classes; decorated command/query handlers are thin Nest adapters that delegate to plain services constructed by feature factories. Commands perform state changes; query services depend only on models, messages, other read operations, and read ports. They must not import write ports, mutating operations, ORM clients, or buses. Keep read/write interfaces distinct even when one repository and database implement both. Add events or sagas when a capability needs them.

Declare account admission through `@UseGuards(AccountAdmissionGuard)`. This guard validates HTTP query input before dispatching `ResolveAccountCommand` to verify the session and ensure its Gloups account exists, then attaches the verified identity to that request using a private symbol. The controller dispatches `GetCurrentAccountQuery` with that admitted identity and fails closed without it. Nest runs guards before parameter pipes, so validation must stay before the provisioning command. Preserve this first-access provisioning behavior explicitly; queries never create missing accounts. Better Auth's own HTTP protocol stays within its integration.

Cross-feature imports must use an explicit public contract. Export only the TypeScript contracts and Nest provider tokens a consumer needs. Keep SDK engines private. The official `@nestjs/drizzle` integration registers a framework-global database token; only repositories, integrations, and approved wiring may import its decorators or resolve that token. Controllers, guards, and business services use owned ports instead. Keep both source imports and Nest module dependencies acyclic; `forwardRef` is not a way around that rule.

Register the named identity database through `DrizzleModule.forRootAsync()` so each Nest application owns its pool. The Nest adapter closes connections on application shutdown. Database readiness runs during module initialization before HTTP listening and remains a live query for `/healthz`. The standalone migration entry point owns and closes its own short-lived client. Do not create a shared database instance outside Nest and pass it into `forRoot()`.

Use static `@Module` imports for the fixed capability graph. Dynamic modules are for actual registration options, such as `DrizzleModule.forRootAsync()` and `CqrsModule.forRoot()`, rather than passing configured modules through feature factories. `ApiConfigModule` provides validated configuration once per application through the plain `ApiConfig` contract. Plain abstract classes can also serve as typed provider tokens without introducing Nest into business ports. Authentication owns its Nest middleware and keeps the HTTP handler private; only its session contract is exported to accounts.

Register each new source file's feature and responsibility in `tools/architecture-policy.ts`. This explicit policy does not infer responsibilities from folder or filename conventions. Update public contracts, permitted Nest exports, and approved external framework modules deliberately. CQRS handlers cannot access repositories or integrations directly. `bun run check:boundaries` checks the policy and its regression fixtures in CI; `bun run test:cqrs` exercises the real compiled Nest buses with isolated business ports.

During organizational refactors, preserve HTTP contracts, authentication policy, SQL migrations, provider behavior, and readiness semantics. Keep unrelated fixes separate and rerun the existing acceptance journeys.

API and mobile acceptance tests use Army `e2e`. API specs use an engine-free target, `fetch`, schema/value matchers, and a serial group with disposable PostgreSQL/API fixtures. Mobile specs use `@e2e-dev/mobile` with iOS/Android targets and synthetic credentials. Keep Node's test runner for unit and architecture checks; do not introduce API acceptance tests under it. `bun run test:api` is the API acceptance gate.

Run `bun run check:nest` after Nest changes. The pinned doctor scans the whole project without inspecting Git history. The commit hook and CI require 100/100, zero findings at every severity, and zero rule failures. Never add doctor suppression directives, disable rules/categories, or narrow coverage through configuration; the gate rejects those bypasses across current repository files, including documentation. Additive custom rules are allowed. Declare intentionally anonymous readiness with `@Public()`; account admission remains guarded. The rate-limit table has real creation/update audit columns in addition to its vendor-owned `lastRequest` window timestamp. Schema changes require additive migrations and Army persistence checks.
